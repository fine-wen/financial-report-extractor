# 企业财务资料工作台（第一版）

这是企业知识中台的第一版可运行产品，先完成一个真实闭环：

> 建立企业 → 上传财务 PDF → 自动提取指标 → 显示原文证据 → 人工复核 → 形成财务档案 → 导出 Excel

项目长期建设初衷、阶段顺序、对抗性审查方法和固定验收线见 [`PROJECT_CHARTER.md`](PROJECT_CHARTER.md)。后续功能和修复都应以该基线为准，避免随着对话和功能增加偏离目标。

## 直接启动

双击 `启动平台.bat`。首次启动会在当前文件夹创建独立运行环境并安装所需组件，完成后浏览器会自动打开：

```text
http://127.0.0.1:8000
```

启动后平台和 MinerU 由后台服务持续运行，关闭浏览器不会停止识别。MinerU 需要单独准备运行环境和本地模型。

## 仓库与本地资料

本仓库现为企业财务资料工作台，替代旧版 `run_extract.py`、`batch_extract.py` 命令行入口；旧版代码仍保留在 Git 提交历史中。

仓库只同步程序、配置示例、文档和使用构造数据的公开测试。本机数据库、客户 PDF、税务资料、客户清单、模型、运行日志、复核记录、一次性数据修复脚本及真实报告回归样本由 `.gitignore` 排除。换电脑时需另外安全迁移 `data/`、`storage/` 和本地模型，克隆仓库不会带回这些业务资料。

日常同步前先检查改动，再提交并推送：

```powershell
git status
git diff
git add <需要同步的文件>
git commit -m "说明这次修改"
git push origin main
```

扫描识别需要在项目的 `.mineru` 中安装 MinerU，并在 `.mineru-models/models/` 下准备 `OpenDataLab--PDF-Extract-Kit-1.0/snapshots/master` 和 `OpenDataLab--MinerU2.5-Pro-2605-1.2B/snapshots/master` 两个模型目录。语言检测模型位于 `%USERPROFILE%/mineru-runtime-data/lid.176.ftz`。`start-mineru.ps1` 会检查模型文件并生成本项目的本地路径配置，避免沿用另一台电脑的旧目录。复制 `.env.example` 为 `.env`，设置本机 MinerU 地址后启动。

## 第一版已经具备

- 企业档案建立与列表管理。
- 支持按行粘贴企业名称，或从 Excel 复制“企业名称、统一社会信用代码、所属行业、联系人”四列后批量新建企业；重复企业自动跳过。
- PDF 财务资料上传与重复文件识别；单家企业可一次选择多份 PDF。
- 文档中心支持文件夹批量导入：既可以选择一家企业文件夹直接上传其中多份 PDF，也可以选择多家企业的总文件夹；开头的数字序号会自动去除，已有企业自动匹配、未建档企业自动新建，重复文件自动跳过，所有文件按选择顺序进入处理队列。
- 文档中心也支持“按内容匹配企业”：可一次选择不同企业的多份 PDF，用前 3 页可提取文字精确匹配已建档企业；不唯一或无法读取时不自动归属，原文件不会进入档案。
- 文档中心可作废上传错误或已更新的文件；作废后保留文档记录和原始 PDF，但删除该文件产生的全部字段，并允许重新上传相同文件。
- 多份报告可以连续上传，系统严格按照提交顺序逐份识别，避免多个 MinerU 任务同时占用本机资源；平台重启后会自动续跑未完成任务。
- 后台处理状态、失败原因和重新处理。
- 核心报表缺指标且已有 MinerU 缓存时，可选择“只补读疑点页”：系统只对相关原页尝试本机二次 OCR，只有原已提取数值不变、缺项的两个年度都有直接来源且资产负债严格勾稽时才接受；否则继续报失败并要求核对原 PDF。
- 页面不做定时自动刷新，避免查看和复核过程中跳动；后台识别继续运行，点击右上角“刷新数据”可查看最新状态。
- 每份报告在文档中心显示识别结果检查摘要，包括识别年度、报表口径、三张主表完整性、资产勾稽、原始与计算指标数量、待复核及重点项数量。
- 资产负债表、利润表和现金流量表中 40 余项常用指标识别。
- 税务资料按首页表名分流：增值税及附加税费申报表提取“一般项目—应纳税额合计—本年累计”；企业所得税年度纳税申报主表 A100000 提取第 36 行“实际应纳所得税额”；企业所得税月（季）度预缴表 A200000 提取第 40 行“本期实际应补（退）所得税额”；税收完税证明按原表顺序逐行提取实缴（退）金额，同一税种的多行分别保存，明细总和必须与证明合计一致。四类资料独立进入税务档案，不进入审计报告财务档案及财务导出。
- 税务资料先核对纳税人名称，再按税款所属期间归属：年报为年度，月度增值税为年月，季度预缴为季度；完税证明每行保留自己的所属期、入（退）库日期、税种、金额、页码及原文证据。完税证明的填发日期不作所属期；退款保留负数，跨年度明细不合并；完税金额不能与申报表“应纳税额”直接相加。所有结果需人工复核；明细、合计或关键信息不清的文件停止取数。
- 已按 `finance_wide.xlsx` 增加短期负债、长期负债，以及同比增长率、复合增长率、研发投入占比、资产负债率和净利率等计算指标。
- 财务档案、人工复核和Excel导出均以 `finance_wide.xlsx` 的23项刚需指标顺序为主顺序；平台扩展指标排列在其后。
- 同一份审计报告同时存在合并报表和母公司报表时，只读取母公司资产负债表、母公司利润表、母公司现金流量表和报告末尾单独列示的母公司财务报表主要项目注释；如果母公司页面是图片且尚未连接 OCR，系统会停止提取，避免误用合并口径。
- 数值、单位、年度、来源页码和原文片段共同保存。
- 同一份年度审计报告同时提取本期数和上期数，并分别保存为两个年度；不同报告出现同一年度数据时保留全部来源，财务档案和导出优先采用较晚报告披露的比较数据。
- 资产与负债加所有者权益的勾稽检查。
- 逐项确认、修改确认和标记缺失。
- 人工复核按重点项、普通项和计算指标排序，可按类别筛选、勾选后批量确认，并支持“保存并复核下一项”。
- 复核人、复核时间和修改前数值留痕。
- 人工确认、修正或排除的指标按文件与年度持久保存；规则重处理时复用这些决定，不再被 OCR 原值悄悄覆盖。
- 企业财务档案汇总。
- Excel 导出。
- 关键操作记录。
- 手机和电脑自适应中文界面。

## 当前边界

文本型 PDF 会先读取文件自带的文字层，再按财务指标名称定位数值，同时保留页码和原文。相邻的本期数和上期数会作为两个独立数字处理。扫描型 PDF、“附注可复制、母公司主表为图片”的混合型 PDF，以及文字层粘连或缺失核心字段的 PDF，会自动交给 MinerU 按原有路线识别整份原文件；平台不再拆分候选页，也不强制指定单一模型。以横向扫描页为主且首次识别仍不完整时，平台会保持原有页序、校正横向页方向后再识别一次。合并与母公司并存时只选母公司页，之后进入同一套指标提取、证据保存和人工复核流程。

取数后会再经过多证据审查：联合检查附注号和行号格式、金额数量级、总计与小计、资产负债勾稽、差额是否恰好对应某个漏项，以及同一家企业不同年度报告中的同年度数据。发现疑点时会在文档状态和人工复核页说明原因并提高复核优先级，不自动改写原始数据；无法确认的关键口径仍停止入库。

若同一报告同一年度的资产总额与负债加所有者权益出现超过 10% 且超过 10 万元的严重差额，该年度来源仍保留供复核，但不会进入财务档案或指标导出；有其他报告的同年度数据时自动回退到其他来源。较小差额仍按原有疑点提示处理。

两年比较表会依据每张表自己的“本年/上年”列头归属年度，允许同一报告的主表与附注采用不同列序；列头相互矛盾时停止入库。主营业务收入大于营业收入仍属默认拦截项；只有原报告证明其他业务收入为负、用户核准具体文件与金额后，才记录该文件专属例外，金额变化不会自动放行。

批量导入可以选择单家企业文件夹，例如 `2宁波某某有限公司 / 2025年审计报告.pdf`；也可以选择包含多家企业子文件夹的总文件夹，例如 `总文件夹 / 2宁波某某有限公司 / 2025年审计报告.pdf`。企业名称必须保留“有限公司”“股份有限公司”等完整后缀。总文件夹根目录不要同时散放 PDF，否则企业归属不明确，系统会要求分开上传。税务资料以正文“税款所属期间/时间”和“纳税人名称”为准，不能仅凭文件名或证明填发日期确定归属；无法确认时会明确报错，不会猜测。

审计报告年度优先依据主财务报表和审计意见中的报告期间，文件名只作补充证据。若同一份母公司报表同时列出一个非全年期间（例如 2024 年 1—5 月）及其前两个完整年度，平台只取两个完整年度，并保留原表格行与页码作为证据；不能明确区分列或核心数据不完整时仍停止入库。“按内容匹配企业”目前要求 PDF 首页可提取文字且企业已建档；纯扫描首页仍需先指定企业或按企业文件夹导入，随后由 MinerU 识别报表正文。

年度识别会排除嵌在长数字中的 OCR 编号和明显超出当前时间的年份；文件名以年度开头但中间插入项目名称时也可作为补充证据。利润总额、所得税费用与净利润明显不勾稽时会停止保存该次提取，防止扫描件漏掉负号后把亏损记成盈利。

扫描识别服务在项目根目录新建 `.env` 后配置：

```text
MINERU_API_URL=http://127.0.0.1:8001
```

MinerU 服务需提供 `/tasks` 异步任务接口及对应的状态、结果接口。平台会保存 MinerU 任务编号，平台重启后续接原任务，避免长报告识别完成后因连接中断而堵住队列。未配置时，扫描件会保留在文档中心并显示明确原因，不会猜测财务数字。

平台从 MinerU 的压缩结果中读取 `content_list.json`：它按页包含识别出的文字块和 HTML 表格，不是普通 TXT 或 Word 文件。平台当前将这些块拼接为逐页文字，再依据表格行提取指标；原始扫描 PDF 始终保留。疑点页补读使用本机 `/file_parse` 接口指定原 PDF 页码，不调用外部服务，也不覆盖整份报告的原 OCR 缓存。

财务表格先依据每张表自己的年度列头定位本年、上年，再读取行金额；列位缺失或冲突的表格行不按默认顺序猜测，文档处理结果会保留“未取数”的页码和原因。核心指标因此缺失时仍进入补读或处理失败。现金流量表在四项净额齐全时核对经营、投资、筹资净额与汇率影响之和是否等于现金净增加额；不一致会显示复核提醒，不自动改写数字。资产负债表不平衡继续作为复核风险提示。

平台按 MinerU 实际开始时间计算处理时长，并为长扫描报告保留最长48小时；超过普通报告用时不会提前误报失败。所有文件仍然按顺序处理，避免并行任务耗尽显存。

当前电脑采用“Windows 本机独立 MinerU 服务”：单独使用 Python 3.12 安装 MinerU，启动地址为 `http://127.0.0.1:8001`，平台继续使用现有运行环境，两者互不影响。平台提交整份原文件并使用 `auto` 解析方式，不额外指定后端，由 MinerU 保持原有的 Pipeline、VLM 与 Hybrid 自动处理逻辑。公式识别关闭、表格识别开启。该方式原始财务资料不离开本机，也能使用本机显卡加速。

本机 RTX 5060 Ti 已实测 MinerU 3.4.4 要求的 lmdeploy 0.11.1；该版本的 TurboMind 不包含这代显卡的可执行内核，无法稳定启动，因此继续使用官方 Transformers 路径。在 MinerU 明确支持与新版 lmdeploy 组合前，不强行切换。`MinerU-HTML` 用于网页 HTML 正文提取，不用于本项目的 PDF 财务报表。

当前版本使用本机轻量数据库，适合内部验证和小团队试用。正式多人部署时，再迁移到 PostgreSQL，并增加登录权限、服务器备份和 MinerU 服务。
